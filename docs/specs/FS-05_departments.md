## 1. 범위

| 하는 것 | 하지 않는 것 |
|---|---|
| 레지스트리로 만든 학과 목록을 보여 주기(`ListDepartments`) | 학과 이름을 자유 입력으로 받기(P8, S1-7) |
| 목록에서 1~2개를 골라 저장하기(`SetDepartments`) | 학생지원시스템의 학과 정보로 미리 채우기([06_school_site §3](../layers/data_access/06_school_site.md#3-학과-공지): 온보딩에 학생지원시스템 로그인을 넣지 않는다) |
| 온보딩에서 학과를 꼭 고르게 하기 | Canvas 프로필로 학과를 알아내기(Canvas에는 학과 정보가 없다, 같은 절) |
| 설정 > 일반 > 학과에서 바꾸기 | 학과 레지스트리를 앱 안에서 고치거나 늘리기(사람이 확인해 넣는다, 같은 절) |
| 학과 공지 조회에서 학과를 정하는 규칙(기본값, 다른 학과) | 공지 목록·본문을 가져오고 보이기(FS-09) |

## 2. 기능 요구사항

### F1 학과 목록 (`ListDepartments`)

- **입력**: 없음.
- **출력**: 레지스트리에 있는 학과마다 레지스트리 키와 표시 이름. 화면과 AI가 같은 키를 쓴다.
- 레지스트리에 공지 게시판이 하나도 없는 사이트(부록 A의 `ace`, `chi`, `eng`, `micro`)는 목록에 넣지 않는다(추론, §6).
- 목록의 단위(학과·학부·전공·단과대학·대학원)와 정렬은 레지스트리가 정한다. 이 기능은 레지스트리를 그대로 목록으로 바꾸기만 한다.

### F2 학과 저장 (`SetDepartments`)

- **입력**: 레지스트리 키 1개 또는 2개(복수 전공이면 2개).
- **규칙**:
  - 0개나 3개 이상이면 거부한다.
  - 레지스트리에 없는 키가 하나라도 있으면 거부한다. 일부만 저장하지 않는다.
  - 같은 키를 두 번 넣으면 1개로 본다(추론, §6).
- **출력**: 저장한 학과 목록. `SettingsRepository`에 저장한다. 거부하면 기존 설정은 그대로다.
- 이 유스케이스는 학교 계정 연결과 관계없이 동작한다. 학교 로그아웃(FS-03 F6)은 학과 설정을 지우지 않는다([FS-03](FS-03_school_account.md) F6).

### F3 온보딩의 학과 선택 단계

- 앱이 F1의 목록을 보여 주고, 학생은 그 안에서만 고른다. 자유 입력란은 없다.
- 1개 이상 고르기 전에는 단계를 끝낼 수 없다. 건너뛰기 버튼이 없다(S1-7).
- 2개를 고른 상태에서는 세 번째를 고를 수 없다. 고른 것을 해제하면 다시 고를 수 있다.
- 단계를 끝내면 F2를 부른다. 거부되면 단계에 머물고 원인을 보인다(§3).
- 목록 안에서 찾기(이름 거르기)를 둘지는 정하지 않았다(§6).

### F4 설정 > 일반 > 학과

- 지금 저장된 학과를 보이고, F3과 같은 선택 방식으로 바꾼다. 저장은 F2다.
- 학과를 모두 비울 수 없다(F2의 1~2개 규칙).
- 바꾸면 그 뒤의 학과 공지 조회(F5)에 바로 쓰인다. 대화 기록은 바뀌지 않는다.

### F5 학과 공지 조회의 학과 결정

학과 공지 조회 유스케이스(FS-09)가 어느 학과를 조회할지 정하는 규칙이다.

| 요청 | 조회할 학과 |
|---|---|
| 학과 인자 없음 | 설정에 저장된 학과 전부(2개면 2개 모두, S1-7) |
| 학과 인자 있음(레지스트리 키) | 그 학과. 내 학과가 아니어도 조회한다(공지는 공개, S5-3). 설정은 바꾸지 않는다 |
| 학과 인자가 레지스트리에 없음 | 거부한다. 학교 사이트에 요청을 보내지 않는다([entrypoints §4](../layers/04_entrypoints.md#4-cdx-명령)) |

- 인자는 레지스트리 키만 받는다. "간호학과" 같은 학생의 말을 키로 바꾸는 일은 AI가 한다. AI가 키 목록을 얻는 방법은 정하지 않았다(§6).
- 한 학과에 공지 게시판이 여럿이면(예: 간호학과 3개) 기본으로 그 학과의 공지 게시판 전부를 조회한다(추론, §6).
- 학과를 2개 조회하면 결과는 학과별로 나뉘고, 각 묶음에 학과 이름이 붙는다(S5-2 성공 상태 "학과 이름과 최근 공지 목록").

## 5. User Flow (UF-05)

이 기능의 [Design Process ①](../03_design_process.md)에서 그린다. 그릴 갈래: 온보딩 학과 선택(1개, 2개, 고르지 않고 진행 시도), 설정에서 바꾸기, 학과 공지 조회의 학과 결정(인자 없음, 다른 학과, 레지스트리에 없는 학과).

## 6. 미확인 항목

- **잘못된 입력의 application 오류가 없다.** [application §4.5](../layers/02_application.md#45-application-오류)의 오류 중 "목록 밖 값·개수 위반"에 맞는 것이 없다(`Rejected`의 사유는 `UserDeclined`, `PolicyDenied`, `LimitExceeded`, 로그인 관련뿐). [entrypoints §4](../layers/04_entrypoints.md#4-cdx-명령)는 "레지스트리에 없는 값은 거부한다"고만 쓴다. 아키텍처에 없음 → UX Strategy §12 후보(예: `Rejected`에 입력 검증 사유를 더하거나 별도 오류). 설정 없음·설정 저장 실패도 같다
- **AI가 학과 키 목록을 얻는 방법.** `ListDepartments`는 [application §3](../layers/02_application.md#3-유스케이스-후보)에 있지만 `cdx` 명령으로 내놓는지는 정하지 않았다([entrypoints §9](../layers/04_entrypoints.md#9-미확인-항목) `cdx` 명령 목록). S5-3에서 AI가 "간호학과"를 레지스트리 키로 바꾸려면 필요하다. 아키텍처에 없음 → UX Strategy §12 후보
- **학교 로그아웃 상태에서 공지 조회.** 학교·학과 공지는 로그인 없이 공개다([06_school_site §1](../layers/data_access/06_school_site.md#1-공통-학교-홈페이지-cms-2026-11-08-확인)). 그런데 [UX Strategy S10-3](../06_ux_strategy.md#a10-앱의-데이터보안-정책이-궁금한-사람) 점검 방법은 "로그아웃 뒤 데이터 질문에 연결 안내가 나오고"라고 쓴다. 학과 공지 질문도 연결 안내를 내는지, 로그인 없이 답하는지 정해야 한다(FS-09와 같은 항목)
- 레지스트리의 선택 단위: [06_school_site §3](../layers/data_access/06_school_site.md#3-학과-공지)은 "학생은 여러 단계(단과대학·학부·전공)의 공지를 봐야 할 수 있다"고 쓰지만, S1-7은 "학과 1~2개"만 정한다. 학과를 고르면 상위 학부·단과대학 공지도 함께 조회할지, 단과대학·대학원·기관(부록 A)도 목록에 넣을지 레지스트리를 만들 때 정한다
- 공지 게시판이 여럿인 학과의 기본 조회 범위(F5). 전부 조회(추론)와 학과 공지(학사) 하나만 조회 중 무엇을 쓸지. 레지스트리에 게시판별 "기본 포함" 표시를 둘지와 함께 정한다
- 공지 게시판이 없는 사이트를 목록에서 뺄지(F1, 추론). 빼지 않으면 그 학과를 고른 학생의 기본 조회가 항상 빈다
- 같은 키를 두 번 넣었을 때 1개로 볼지 거부할지(F2, 추론). 화면에서는 생길 수 없고 `cdx`로는 `SetDepartments`를 부를 수 없으므로(`cdx`에 설정 명령이 없다고 본다) 영향은 작다
- 레지스트리를 앱에 어떻게 싣고 갱신하는지(앱 업데이트로만 바꾸는지). 저장된 학과가 새 레지스트리에 없을 때의 동작(§3, 추론)이 이에 달려 있다
- 학과 목록(F1)이 학과 44곳 이상이면 목록 안 찾기가 필요할 수 있다. 자유 입력이 아니라 목록 거르기이므로 P8과 맞지만 UX Strategy에 정해진 것이 없다. Design Process ②·③에서 정한다
