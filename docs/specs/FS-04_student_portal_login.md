# FS-04 학생지원시스템 로그인

| 항목 | 내용 |
|---|---|
| 독자 | 개발자 본인, 후속 문서·구현을 돕는 AI 에이전트 |
| 상태 | 초안 |
| 시나리오 | S2-3, S6-1, S6-2 ([UX Strategy §4](../06_ux_strategy.md#4-actor와-시나리오)) |
| 화면 | 학생지원시스템 로그인 창(대화 위에 뜨는 창), 설정 > 연결 > 학생지원시스템, 연결 알약, 연결 로그아웃 확인 창 ([UX Strategy §7.2](../06_ux_strategy.md#72-mvp-화면), [§7.5](../06_ux_strategy.md#75-설정)) |
| 유스케이스 | 아키텍처에 이름이 없다(§6). 학생지원시스템 데이터를 조회하는 유스케이스([FS-10](FS-10_academic_records.md))가 로그인 창을 조율한다 |
| 근거 | [07_student_portal §2](../layers/data_access/07_student_portal.md#2-로그인과-세션), [07_student_portal §3.5](../layers/data_access/07_student_portal.md#35-앱이-지킬-것), [data_access §2.5](../layers/data_access/README.md#25-http--auth--인증과-http-정책), [security §3](../cross_cutting/01_security.md#3-지킬-것과-강제하는-곳) |

> **이 문서의 역할**: 학생이 학생지원시스템(학사행정웹서비스)에 앱으로 로그인하고, 그 세션을 유지·회복·종료하는 기능의 동작과 수용 기준을 정한다.
> 요청 경로와 세션 수명은 [07_student_portal §2](../layers/data_access/07_student_portal.md#2-로그인과-세션), 연결 행의 모양과 상태 체계는 [UX Strategy §7.5](../06_ux_strategy.md#75-설정)와 [FS-06](FS-06_connection_status.md), 성적·학적 조회는 [FS-10](FS-10_academic_records.md)이 맡는다. 학교 계정(Canvas·LearningX·스마트출결) 로그인은 [FS-03](FS-03_school_account.md)이다.

## 1. 범위

| 하는 것 | 하지 않는 것 |
|---|---|
| 학생지원시스템이 필요한 질문을 했을 때 로그인 창 띄우기 | 온보딩이나 앱 시작 때 학생지원시스템 로그인 받기([UX Strategy §7.2](../06_ux_strategy.md#72-mvp-화면)) |
| 저장된 학번·비밀번호로 로그인하기 | 학번을 외부 입력(AI, `cdx` 인자, 화면 입력)으로 받아 요청에 쓰기([07 §3.5](../layers/data_access/07_student_portal.md#35-앱이-지킬-것)) |
| 사용하는 동안 세션 연장하기 | 학교 서버가 주는 연장 수단(`sessionExtend.do`) 밖의 방법으로 세션 늘리기 |
| 세션이 끝났을 때 로그인 한 번으로 하던 요청 이어 가기 | 로그인 실패 뒤 자동으로 반복 시도하기(서버가 실패 횟수를 센다) |
| 로그아웃(세션과 로그인 학번 지우기) | 비밀번호 찾기·변경(화면의 `CONFIRM_OTP`는 비밀번호 찾기용이다) |
| 로그인 학번을 세션과 함께 보관하기 | AI나 `cdx`가 로그인하기([entrypoints §4](../layers/04_entrypoints.md#4-cdx-명령)) |

## 2. 기능 요구사항

### F1 로그인 창을 띄우는 때

- 학생지원시스템 데이터가 필요한 요청(FS-10)이 "로그인 안 됨" 또는 "세션 만료"를 만나면, **그 요청을 처리하던 유스케이스가** 로그인 창을 띄우고 답을 기다린다. 학교 계정의 OTP 창([FS-03 F5](FS-03_school_account.md))과 같은 방식이다.
- 창은 요청을 일으킨 대화 ID를 가진다. 그동안 그 대화의 상태는 "Input"이다([UX Strategy §7.4](../06_ux_strategy.md#74-대화별-상태)).
- 온보딩, 앱 시작, 학교 계정 연결 때는 창을 띄우지 않는다. 학생지원시스템 데이터를 묻지 않는 학생에게는 창이 뜨지 않는다.
- 설정 > 연결 > 학생지원시스템 행의 로그인 버튼으로도 시작할 수 있다([UX Strategy §7.5](../06_ux_strategy.md#75-설정) 연결 행의 행동 버튼).
- 유스케이스가 화면에 로그인을 요청하는 출력 포트는 아키텍처에 없다. [application §4.4](../layers/02_application.md#44-사용자-상호작용과-로컬-저장)에는 `OtpPrompt`만 있다(§6).

### F2 로그인

- **입력**: 학번·비밀번호는 학교 계정 연결([FS-03 F1](FS-03_school_account.md))에서 키체인에 저장한 값을 쓴다([07 §2](../layers/data_access/07_student_portal.md#2-로그인과-세션): 아이디·비밀번호가 같고 같은 저장 값을 쓴다). 창에서 학생은 로그인을 승인한다. 창에 비밀번호 입력 칸을 둘지는 정하지 않았다(추론, §6).
- **동작**: [07 §2](../layers/data_access/07_student_portal.md#2-로그인과-세션)의 1~3단계를 한 번의 시도로 처리한다. 2단계 응답의 `SUCCESS_YN`으로 성공·실패를 나눈다.
- **실패**: 비밀번호가 거부되면(`SUCCESS_YN`이 `Y`가 아님) 자동으로 다시 시도하지 않는다. 학번·비밀번호 확인 안내를 보인다.
- **학교 계정이 연결되지 않음**: 저장된 학번·비밀번호가 없으면 학생지원시스템에 요청하지 않고 학교 계정 연결(FS-03)을 안내한다(추론, §6).
- **출력**: 성공하면 세션 쿠키와 **로그인 학번**을 학생지원시스템용 `SessionStore`에 저장한다([data_access §2.5](../layers/data_access/README.md#25-http--auth--인증과-http-정책): 포털은 `RequestAuthenticator`·`SessionStore` 구현을 따로 두고 로그인 학번도 함께 보관한다). 비밀은 키체인에만 둔다.
- 2단계 응답이 JSON이 아니거나 필드가 없으면, 또는 3단계 뒤 세션이 생기지 않으면 `SourceChanged`로 판정한다. 비밀번호가 틀렸다고 말하지 않는다.

### F3 세션 유지

- 세션 수명과 연장 방법은 [07 §2](../layers/data_access/07_student_portal.md#2-로그인과-세션)를 따른다(60분, `sessionExtend.do`).
- 학생지원시스템 조회가 이어지는 동안에는 세션이 끝나기 전에 연장한다. 학생이 학생지원시스템을 쓰지 않는 동안에는 연장하지 않는다(추론, §6). 연장 시점은 아키텍처가 정하지 않았다.
- 연장은 코어 안에서 한 번에 하나만 돈다(학교 계정 갱신과 같은 원칙, [FS-03 F3](FS-03_school_account.md)).
- 연장에 실패하면(세션이 이미 끝남) 다음 학생지원시스템 요청 때 F4로 간다. 그 전까지 연결 행은 로그인이 필요한 상태다(표시는 FS-06).

### F4 끊긴 세션 이어 가기

- 대화 중 학생지원시스템 요청이 세션 만료를 만나면 F1의 창을 띄운다. 로그인에 성공하면 같은 유스케이스가 **원래 요청을 다시 실행해** 결과를 돌려준다. `cdx` 요청은 그동안 열려 있다가 결과를 받는다(P6, S2-3). 학생은 질문을 다시 보내지 않는다. `cdx`와 AI는 다시 시도하지 않는다.
- 기다리는 시간의 상한은 [FS-03 F5](FS-03_school_account.md)와 같다. 상한을 넘기면 요청은 `NeedsLogin`으로 끝나고 창은 열린 채 남는다. 그 뒤 로그인에 성공하면 대화에 다시 물어 달라는 앱 메시지를 남긴다(문구는 Foundation).
- 창을 닫으면 원래 요청은 `NeedsLogin`으로 끝나고, 대화에는 설정의 학생지원시스템 행으로 가는 버튼이 있는 앱 메시지가 남는다.
- 같은 만료로 여러 요청이 동시에 막히면 창은 하나만 뜬다. 창이 여러 대화 ID를 갖는 방식과 창을 닫을 때의 처리는 [FS-03 F5](FS-03_school_account.md#f5-끊긴-연결-이어-가기)와 같다.
- 학교 계정 세션 만료(OTP)와 학생지원시스템 세션 만료가 함께 일어나도 창은 각각 하나씩이다. 학교 계정 OTP 창이 학생지원시스템 로그인을 대신하지 않는다(로그인 시스템이 다르다, [07 §1](../layers/data_access/07_student_portal.md#1-개요)).

### F5 로그인 학번 (IDOR 방어)

- 학생지원시스템 요청의 학번은 **F2에서 보관한 로그인 학번만** 쓴다. 유스케이스, `cdx` 명령, DS의 공개 인터페이스에 학번 매개변수가 없다. 규칙의 원본은 [07 §3.5](../layers/data_access/07_student_portal.md#35-앱이-지킬-것)다.
- 서비스마다 학번 역할 매개변수(`USER_ID`, `S_USER_NO`, `USER_NO`, `STD_NO` 등)를 **모두** 로그인 학번으로 채운다. 어느 매개변수가 학번인지는 서비스 레지스트리가 정한다.
- 응답에 `USER_NO`·`USER_ID`가 있고 로그인 학번과 다르면 그 응답을 버린다.
- 로그인하지 않은 상태에서는 로그인 학번이 없으므로 학생지원시스템 요청을 만들지 않는다.

### F6 로그아웃

- 설정 > 연결 > 학생지원시스템의 로그아웃 버튼 → 확인 창 → 승인하면 학생지원시스템 세션 쿠키와 로그인 학번을 지운다.
- 학번·비밀번호는 학교 계정의 저장 값이므로 지우지 않는다. 그 값은 FS-03 로그아웃이 지운다.
- 서버 쪽 로그아웃 경로는 기록하지 않았다(§6). 서버 로그아웃을 하지 못해도 로컬은 지우고 로그아웃 상태가 된다.
- 학교 계정 로그아웃([FS-03 F6](FS-03_school_account.md))으로 학번·비밀번호가 지워지면 학생지원시스템 세션도 함께 끝낸다(추론, §6).
- 로그아웃 상태에서는 어떤 자동 동작도 학생지원시스템에 로그인하지 않는다. 로그인은 F1의 창이나 연결 행 버튼에서만 시작한다.

### F7 상태 조회

- 학생지원시스템 세션의 상태(로그인 안 됨, 연결됨, 확인 중)를 돌려준다. 연결 행·알약·대화 안내의 표시는 FS-06이 이 값으로 판정한다([presentation §1](../layers/03_presentation.md#1-개요): `presenters/shell`이 "학생지원시스템 세션"을 입력으로 받는다).
- 키체인 읽기 실패 중 `Locked`, `Misconfigured`는 로그아웃으로 다루지 않는다([data_access §2.5](../layers/data_access/README.md#25-http--auth--인증과-http-정책)).

## 3. 예외

| 상황 | 판정 | application 오류 | 다음 행동(P5) |
|---|---|---|---|
| 비밀번호 거부 | 2단계 `SUCCESS_YN` ≠ `Y`, `ERROR_CODE`(`LOGIN_001` 등) | `Rejected(PasswordIncorrect)` | 학번·비밀번호 확인. 자동 재시도 없음 |
| 실패가 쌓여 잠김 | 잠김 기준 미확인 | 맞는 사유 열거형이 없음(§6) | — |
| 로그인 화면·응답 형식이 바뀜 | `SourceChanged`(실패 단계 이름) | `SourceChanged` | 앱 업데이트가 필요하다는 안내 |
| 네트워크 오류·요청 제한 | `Network`, `RateLimited` | `Temporary` | 다시 시도 |
| 로그인 안 됨·세션 만료(사용 중) | `SessionExpired` | 없음. 유스케이스가 창 안에서 처리하고, 창을 닫거나 대기 상한을 넘기면 `NeedsLogin` | 학생지원시스템 로그인 창(F4) |
| 로그인 창을 닫음 | — | `NeedsLogin` | 학생지원시스템 행으로 가는 버튼 |
| 저장된 학번·비밀번호 없음 | — | `NeedsLogin` | 학교 계정 연결(FS-03) (추론) |
| 응답의 학번이 로그인 학번과 다름 | 응답 검증 실패 | 정해지지 않음(§6) | 응답을 버린다. 다른 학생의 값은 보이지 않는다 |
| 키체인 잠김 | `Locked` | — | 학생에게 보이지 않음. 잠시 뒤 재시도 |

- `NeedsLogin`은 학교 계정 OTP와 학생지원시스템 로그인을 구별하지 않는다. 화면이 어느 창을 띄울지는 요청을 처리하던 유스케이스가 정한다(§6).

## 4. 수용 기준

| # | 기준 | 확인 방법 | 시나리오 |
|---|---|---|---|
| AC1 | 온보딩을 끝내고 학생지원시스템과 관계없는 질문("이번 주 할 일")만 하면 학생지원시스템 로그인 창이 뜨지 않는다 | 온보딩 뒤 질문한다 | S6-1 |
| AC2 | 로그인 전에 성적을 물으면 로그인 창이 뜨고 그 대화가 "Input"이 되며, 로그인 뒤 같은 대화에 실제 값이 나온다 | 실제 계정으로 질문한다 | S6-1 ★ |
| AC3 | 세션이 끝난 뒤 성적을 물으면 로그인 창이 뜨고, 로그인 뒤 원래 질문의 답이 같은 대화에 이어진다. 질문을 다시 보내지 않는다 | 학생지원시스템 쿠키를 지워 만료를 재현한 뒤 질문한다 | S2-3 ★ |
| AC4 | 만료로 요청 두 개가 동시에 막혀도 로그인 창은 하나만 뜨고, 로그인 뒤 두 요청 모두 답이 나온다 | 테스트(메모리 로그인 구현) | S2-3 |
| AC5 | 로그인 창을 닫으면 요청이 `NeedsLogin`으로 끝나고, 대화에 학생지원시스템 행으로 가는 버튼이 있는 앱 메시지가 남는다 | 테스트 + 화면 확인 | S2-3 |
| AC6 | 비밀번호가 거부되면 로그인 요청은 한 번만 나가고, 학번·비밀번호 확인 안내가 나온다 | 2단계 응답을 고정한 테스트(요청 횟수를 센다) | — |
| AC7 | 로그인 응답이 예상 형식이 아니면 비밀번호가 틀렸다는 안내가 아니라 학교 화면이 바뀌었다는 안내가 나온다 | 응답을 고정한 테스트 | — |
| AC8 | `cdx` 명령, IPC 요청 타입(`ipc/wire`), 학생지원시스템 조회 유스케이스의 입력에 학번 필드가 없다 | `cdx <명령> --help` 전수 확인, `ipc/wire` 타입 검사 테스트 | — |
| AC9 | 학생지원시스템으로 나가는 모든 요청에서 서비스 레지스트리의 학번 역할 매개변수가 로그인 학번과 같다 | 메모리 `SessionStore`와 요청 기록 테스트(레지스트리의 모든 서비스) | — |

## 5. User Flow (UF-04)

이 기능의 [Design Process ①](../03_design_process.md)에서 그린다. 그릴 갈래: 질문에서 시작하는 처음 로그인(F1·F2), 끊긴 세션 이어 가기(F4, 창 닫기·대기 상한 포함), 비밀번호 거부·형식 변경(F2), 로그아웃(F6).

## 6. 미확인 항목

- **로그인 창이 무엇을 받는가.** [07 §2](../layers/data_access/07_student_portal.md#2-로그인과-세션)는 "학번·비밀번호는 Canvas 로그인과 같은 저장 값을 쓴다"고 하고, [UX Strategy §7.2](../06_ux_strategy.md#72-mvp-화면)는 학생지원시스템 로그인 창을 C1(비밀 입력과 승인)로 둔다. 저장 값으로 로그인하면 창은 승인만 받는다. F2는 승인만 받는 것으로 추론했다. 비밀번호를 다시 받을지, 저장 비밀번호가 거부되면 학교 SSO 비밀번호도 바뀌었을 것이므로 [FS-03](FS-03_school_account.md) F7과 같이 F1의 입력 화면(학번 유지, 새 비밀번호)으로 보낸다(FS-03에서 정함). 창이 비밀번호를 다시 받을지는 정한다
- **만료 때 창을 띄우는가, 자동으로 다시 로그인하는가.** [data_access §2.5](../layers/data_access/README.md#25-http--auth--인증과-http-정책)는 "세션 만료 시 재로그인, 로그인 실패 잠김 처리는 그 구현에 둔다"고 써서 `auth` 구현이 저장 값으로 자동 재로그인하는 것으로 읽힌다. [UX Strategy S2-3](../06_ux_strategy.md#4-actor와-시나리오)은 "학생지원시스템 로그인 창이 뜨고, 로그인하면 조회가 이어진다"고 쓴다. 2차 인증이 없으므로 자동 재로그인은 기술적으로 가능하다. 이 문서는 S2-3을 따라 F4를 썼다. 어느 쪽인지 정하고 다른 문서를 고친다
- **아키텍처에 없음 → [UX Strategy §12](../06_ux_strategy.md#12-아키텍처에-올릴-것) 후보**:
  - 학생지원시스템 로그인·로그아웃·상태 조회 유스케이스. [application §3](../layers/02_application.md#3-유스케이스-후보)의 학교 로그인 묶음에는 `LoginWithOtp`, `Logout`, `GetAuthState`만 있다. [UX Strategy §11](../06_ux_strategy.md#11-대응표)에는 "학생지원시스템 로그인" 행이 있다
  - 유스케이스가 학생지원시스템 로그인 창을 요청하는 출력 포트. [application §4.4](../layers/02_application.md#44-사용자-상호작용과-로컬-저장)에는 `OtpPrompt`만 있다. `OtpPrompt`를 넓힐지 새 포트를 둘지 정한다
  - `NeedsLogin`의 대상 구분. [application §4.5](../layers/02_application.md#45-application-오류)는 "학교 재로그인(OTP)이 필요하다"로 정의하고, [UX Strategy §8](../06_ux_strategy.md#8-상태-오류-긴-작업)은 "해당 로그인 창(OTP, 학생지원시스템)"으로 쓴다
  - 학생지원시스템 로그인 잠김을 나타내는 `Rejected` 사유(지금 열거형의 `OtpLocked`는 OTP용이다). 잠김 기준을 확인한 뒤 필요하면 더한다
  - 응답 학번이 로그인 학번과 달라 버렸을 때의 application 오류
- 학생지원시스템의 서버 로그아웃 경로. [07_student_portal](../layers/data_access/07_student_portal.md)에 기록이 없다. 로그아웃 상태에서 한 번 기록한다
- 학교 계정 로그아웃이 학생지원시스템 세션도 끝내야 하는지(F6, 추론). 학번·비밀번호가 지워지면 다시 로그인할 수 없으므로 함께 끝내는 쪽으로 추론했다
- 학교 계정 없이(저장 값 없이) 학생지원시스템만 쓰는 경우를 허용할지(F2, 추론)
- 세션 연장 시점과 유휴 기준(F3, 추론). [07 미확인](../layers/data_access/07_student_portal.md#미확인-항목)의 "연장만으로 60분 넘게 유지되는지, 최대 유지 시간"을 확인한 뒤 정한다. AC11은 이것에 달려 있다
- 3단계 뒤 리디렉션 경로와 세션 쿠키 이름, 로그인 실패 잠김 기준([07 미확인](../layers/data_access/07_student_portal.md#미확인-항목))
- 학생지원시스템 행에서 "곧 만료" 상태를 쓸지(60분 세션). 표시는 FS-06에서 정한다
