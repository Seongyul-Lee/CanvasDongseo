# CanvasDongseo — UX Strategy

| 항목 | 내용 |
|---|---|
| 독자 | 개발자 본인, 후속 문서·구현을 돕는 AI 에이전트 |
| 근거 | [PRD](01_prd.md), [System Architecture](02_system_architecture.md)와 레이어별 문서, [Security](cross_cutting/01_security.md), T3 Code `v0.1.8-nightly.20261109.4399`(§3) |

> **이 문서의 역할**: 어떤 경험을 지향하고 판단이 갈릴 때 무엇을 고르는지, 무엇이 화면이고 각 화면이 왜 있는지 정한다. 근거는 Actor별 시나리오다.
> 단계와 분기는 User Flow, 기능별 상세와 수용 기준은 Functional Spec, 디자인 절차와 정확한 문구·용어·표기 규칙은 [Design Process](03_design_process.md), 코드 구조는 [Presentation](layers/03_presentation.md), 막아야 할 것의 규칙은 [Security](cross_cutting/01_security.md)가 맡는다.

## 1. 범위와 경계

### 1.1 범위

- **이 문서의 범위는 항상 현재 아키텍처 설계 범위와 같다.** 아키텍처에 기능이 더해지면 이 문서도 그만큼 늘어난다. 아키텍처에 없는 기능을 이 문서가 새로 만들지 않는다.
- 범위가 어긋나지 않았는지는 §11 대응표로 확인한다. 아키텍처에 기능을 더하면 대응표에 행을 더하고, 행에 시나리오와 화면을 채운다.
- 경험상 필요하지만 아키텍처에 없는 것은 §12에 적고, 설계 변경은 해당 문서에서 따로 한다.
- **§12에 걸린 시나리오와 화면은 반영 전까지 보류다.** 해당 시나리오와 화면에 `[보류: §12 ⑧]`처럼 표시한다. 보류 시나리오는 백로그에 올려도 구현 대상이 아니며, ⑥ 시나리오 점검에서도 "보류"로 적는다. §12 항목이 반영되면 표시를 지운다.

### 1.2 맡는 것과 맡지 않는 것

| 질문 | 맡는 문서 |
|---|---|
| 왜 만들고, 누구를 위해, 어디까지 만드는가 | [PRD](01_prd.md) |
| 어떤 경험을 지향하고, 판단이 갈릴 때 무엇을 고르는가. 무엇이 화면이고 각 화면은 왜 있는가 | **이 문서** |
| 어떤 순서와 분기로 움직이는가 | User Flow(각 [Functional Spec](specs/README.md)의 `UF-NN`, [Design Process](03_design_process.md) ①에서 그린다) |
| 정확히 무엇을 하고, 입출력·예외는 무엇이며, 언제 성공으로 보는가 | [Functional Spec](specs/README.md) |
| 어떻게 보이는가, 정확한 문구·용어·한글 표기 | [Design Process](03_design_process.md)의 Foundation과 기능별 산출물 |
| 코드에서 어디에 두는가 | [Presentation](layers/03_presentation.md) |
| 무엇을 막아야 하는가 | [Security](cross_cutting/01_security.md) |

- 다른 문서가 이미 정한 결정은 §2에 링크만 건다. 그 결정을 바꿔야 하면 이 문서에서 바꾸지 않고 해당 문서의 수정으로 올린다.
- 화면 단위의 단계나 수치를 쓰고 싶어지면 User Flow나 Functional Spec으로 넘긴다.

| 한글 글꼴 | 우리가 고른다. 크기와 색은 그대로 둔다. 화면이 깨질 때만 줄 간격을 고친다 |

**라이선스와 상표**

- 가져온 코드에는 저작권·라이선스 문구를 남기고, 앱 안에서는 설정 > 앱 정보 > 오픈소스 라이선스에 고지한다. 서드파티 패키지(lucide는 ISC 등)도 함께 고지한다. 절차는 [platform §1](cross_cutting/02_platform.md).
- UI 아이콘(lucide)과 T3 Code가 직접 그린 아이콘은 그대로 쓴다.
- 다른 회사의 로고(Claude 등)는 연결 대상을 표시할 때만 쓰고, 각 회사의 브랜드 가이드라인을 따른다. 우리 앱이 그 회사의 공식 제품처럼 보이게 하지 않는다.
- T3 Code의 이름, 워드마크, 앱 아이콘은 쓰지 않는다. MIT는 상표 권리를 부여하지 않는다.

## 4. Actor와 시나리오

- **Actor**는 고유한 한 사람이 아니라, **같은 목적을 가진 사용자 집단**이다. 목적 묶음 단위로 나누고, 세밀한 목적은 그 아래 시나리오로 둔다. 코드 쪽의 "변경 Actor"([build_ci §2.1](cross_cutting/03_build_ci.md))와 다른 뜻이다([용어](02_system_architecture.md#4-용어)).
- 시나리오는 **상황, 목적, 성공 상태, 점검 방법** 네 칸으로 쓴다. 성공 상태는 눈으로 확인할 수 있는 문장으로 쓰고, 점검 방법은 [Design Process ⑥ 시나리오 점검](03_design_process.md)에서 실제 앱으로 따라갈 기준이다.
- 시나리오 번호는 백로그 이슈와 PR이 참조하므로 바꾸지 않는다. 없애면 번호를 비워 두고, 더하면 다음 번호를 쓴다.
- 일부 점검 방법(S3-2, S5-2, S6-2 등)은 실제 학교 계정과 서버가 있어야 확인할 수 있다.

### A1 앱을 처음 쓰기 시작하려는 사람

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S1-1 | 설치 직후이고, Claude Code를 써 본 적이 없다 | AI를 연결해 첫 질문을 보낸다 | 설치 전에 "Claude 유료 플랜이 필요하다"는 조건이 보인다. 앱 안에서 설치에 동의하고 브라우저로 로그인한 뒤 대화창에 첫 응답이 나온다 | `claude`가 없는 유료 계정으로 터미널을 열지 않고 첫 응답까지 간다 |
| S1-2 | Free 플랜 계정으로 로그인했다 | 왜 안 되는지와 해결 방법을 안다 | Free 플랜은 Claude Code를 쓸 수 없다는 안내와 유료 플랜 안내가 보이고, 대화는 시작되지 않는다 | Free 계정으로 로그인하면 해당 안내가 표시되고, 로그아웃 등 다른 안내와 구별된다([application §4.5](layers/02_application.md#45-application-오류)) |
| S1-3 | 이미 Claude Code를 쓰고 있다 | 다시 설정하지 않고 바로 쓴다 | AI 로그인 단계 없이 대화창이 열리고, 쓰던 스킬을 부를 수 있다 | 로그인된 계정에서 첫 실행 때 AI 로그인 단계가 나오지 않고, 기존 스킬 하나가 실행된다 |
| S1-4 | OTP를 등록한 학생이 학교 계정을 연결한다 | 학교 데이터를 쓸 수 있게 한다 | 학번, 비밀번호, OTP를 한 번 입력하면 연결됨 상태가 보인다 | 연결 뒤 "이번 주 할 일" 질문에 실제 데이터로 답한다 |
| S1-5 | OTP를 등록하지 않은 학생이 연결하려 한다 | 등록을 마치고 연결한다 | 미등록이라는 안내와 브라우저 등록 버튼이 보이고, 등록 뒤 돌아와 S1-4를 마친다 | 미등록 판정 때 안내와 버튼이 표시되고, 버튼을 누르면 OS 브라우저에서 등록 페이지가 열린다 |
| S1-6 | 공인인증서만 쓰는 학생이 연결하려 한다 | 쓸 수 있는지 판단한다 | 지원하지 않는다는 안내와 OTP 등록이라는 대안이 보인다 | 2차 인증 수단 없음으로 판정되면 해당 안내가 표시된다 |
| S1-7 | 첫 온보딩에서 학과를 정한다 | 내 학과 공지를 받을 수 있게 한다 | 학과 선택은 건너뛸 수 없다. 앱이 주는 목록에서만 고르고, 복수 전공이면 2개를 고른다 | 학과를 고르지 않으면 온보딩이 끝나지 않고, 자유 입력란이 없다. 2개를 고른 뒤 "학과 공지"를 물으면 두 학과의 공지가 나온다([06_school_site §3](layers/data_access/06_school_site.md#3-학과-공지)) |

### A4 과목 내용과 자료를 찾아보려는 사람

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S4-1 | 과제가 무엇을 요구하는지 알고 싶다 | 요구 사항을 이해한다 | 요약과 함께 원문 링크가 보인다 | 원문 링크를 누르면 OS 기본 브라우저에서 과제 페이지가 열린다 |
| S4-2 | 강의 자료를 찾는다 | 자료를 열거나 받는다 | 자료 목록과 열기·받기 수단이 보인다 | 자료 하나를 받으면 정해진 폴더에 파일이 생긴다 |
| S4-3 | 게시판에서 다른 학생이 쓴 글을 확인한다 | 내용을 안전하게 본다 | AI 응답이 요약임이 표시되고, 원문은 우측 패널에서 열린다 | `Peer` 글을 물으면 요약 표시와 원문 보기가 나오고, 이후 같은 대화에서 시점 경고가 한 번 나온다 |

### A5 학교·학과 공지를 확인하려는 사람

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S5-1 | 장학금이나 학사 일정 공지를 찾는다 | 관련 공지를 얻는다 | 공지 제목, 게시일, 원문 링크가 보인다 | 링크를 누르면 OS 브라우저에서 해당 공지가 열린다 |
| S5-2 | 우리 학과의 최근 공지가 궁금하다 | 학과 소식을 안다 | 학과 이름과 최근 공지 목록이 보인다 | 목록이 학과 사이트의 최신 글과 같다 |
| S5-3 | 다른 학과의 공지를 묻는다 | 그 학과 공지를 본다 | 내 학과가 아니어도 AI가 해당 학과 공지를 조회해 답한다. 공지는 누구나 볼 수 있다 | "간호학과 공지 보여 줘"에 실제 간호학과 공지가 나온다 |

### A6 내 학적 상태를 확인하려는 사람

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S6-1 | 성적, 이수 학점, 학적 정보가 궁금하다 | 내 상태를 안다 | 학생지원시스템 로그인이 필요하면 로그인 창이 뜨고, 로그인 뒤 답이 나온다 | 로그인 전에는 로그인 창, 로그인 뒤에는 실제 값이 나온다 |
| S6-2 | 내 출결 현황이 궁금하다 | 결석·지각 여부를 안다 | 과목별 출결 기록이 보인다 | 응답 내용이 학생지원시스템 과목출결조회 화면의 값과 같다. 스마트출결을 쓰는 수업은 아직 옮겨지지 않은 전자출결 기록이 참고로 구별돼 보인다 |

### A7 강의로 공부하려는 사람

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S7-1 | 강의 동영상으로 슬라이드 PDF와 스크립트를 만든다 | 복습 자료를 얻는다 | 사이드바의 해당 대화에 "작업 중"이 보이고, 그동안 다른 대화를 쓸 수 있다. 끝나면 "완료"로 바뀌고 대화에 결과 파일 위치가 보인다 | 작업 중에 다른 대화에서 질문해도 답이 나오고, 완료 뒤 상태가 바뀌며 학기/과목 폴더에 파일이 생긴다 |
| S7-2 | 진행 중인 작업을 멈추고 싶다 | 작업을 취소한다 | 대화 안의 작업 카드에 취소 버튼이 있고, 누르면 취소된 상태가 된다 | 취소하면 작업 상태가 `cancelled`가 되고 결과 파일이 남지 않는다 |
| S7-3 | 만들어 둔 스크립트로 공부한다 | 요약, 퀴즈, 예상 시험지를 얻는다 | 대화로 결과가 나오고, 어떤 스크립트를 썼는지 보인다 | "3주차 요약해 줘"에 대한 응답이 해당 스크립트 파일을 근거로 표시한다 |
| S7-4 | 동영상이나 자료를 내려받는다 | 파일을 갖는다 | 저장 위치가 보인다 | 받은 파일이 표시된 위치에 있다 |

|---|---|---|---|---|
| S8-1 | 과제 마감을 내 캘린더나 플래너에 넣는다 | 일정을 기록한다 | 코어가 만든 기록 내용의 확인 창이 뜨고, 승인한 뒤 반영 완료가 보인다 | 승인하면 Canvas에 일정이 생기고, 거부하면 생기지 않는다 |

### A9 AI를 자기 방식대로 쓰려는 사람

다른 AI 제공자(Codex, Gemini, Grok)의 시나리오는 아키텍처에 제공자별 설계가 생기면 더한다.

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S9-1 | 모델을 바꾸거나 `/compact`를 쓰거나 스킬을 쓴다 | 터미널에서처럼 쓴다 | 입력창 자동 완성에 커맨드가 보이고 실행 결과가 나온다 | `/model`, `/compact`, 스킬 하나가 각각 동작한다 |
| S9-2 | 지원하지 않는 커맨드를 입력했다 | 대안을 안다 | 지원하지 않는다는 안내와 대신 할 일이 보인다 | `/config`를 입력하면 안내가 표시되고 CLI로 넘어가지 않는다 |
| S9-3 | 새 대화를 시작하거나 지난 대화로 돌아간다 | 원하는 대화를 이어 간다 | 대화 목록에서 고른 대화가 이전 내용과 함께 열린다 | 앱을 다시 시작한 뒤 지난 대화를 열고 질문하면 맥락이 이어진 답이 나온다 |

### A10 앱의 데이터·보안 정책이 궁금한 사람

| # | 상황 | 목적 | 성공 상태 | 점검 방법 |
|---|---|---|---|---|
| S10-1 | 비밀번호와 세션이 어디에 저장되고 AI에게 넘어가는지 궁금하다 | 안심하고 쓴다 | 설정 > 정책에서 저장 위치(OS 키체인)와 AI가 보는 범위(조회 결과만, 비밀 없음)를 본다. AI에게 물어도 같은 내용으로 답한다 | 설정에서 정책 화면에 들어갈 수 있고, "내 비밀번호 AI가 볼 수 있어?"의 답이 정책 화면 내용과 같다([application §3](layers/02_application.md#3-유스케이스-후보) `GetPolicy`) |
| S10-2 | 앱이 내 대신 무엇을 하고 무엇을 하지 않는지 궁금하다 | 범위를 안다 | 같은 경로에서 하지 않는 일(제출, 출결, 신청, 강의평가)과 확인 뒤 하는 일(캘린더, 플래너)을 본다. AI도 같은 내용으로 답한다 | S10-1과 같다 |
| S10-3 | 앱을 그만 쓰려고 한다 | 연결과 내 파일을 정리한다 | 학교·AI 로그아웃은 설정에서 하고, 내려받은 파일과 학습 결과물은 AI에게 요청해 지운다 | 로그아웃 뒤 데이터 질문에 연결 안내가 나오고, "다운로드 받은 동영상 모두 지워 줘"는 권한 확인을 거쳐 폴더를 비운다 |

- **다루지 않는 것**: 앱 내부 데이터(대화 기록, 설정, HMAC 기록)의 삭제는 MVP 범위가 아니다. AI가 앱 데이터 폴더를 직접 지워서 생기는 결과에 대해 MVP에서는 앱이 책임지지 않는다.
- 키체인 항목은 AI가 지울 수 없다. 학교 로그아웃이 세션을 지운다.

## 5. 경험 원칙

판단 기준이다. 원칙마다 판단이 갈릴 때 고르는 쪽과 근거 시나리오를 둔다.

| # | 원칙 | 판단이 갈릴 때 고르는 것 | 근거 |
|---|---|---|---|
| P0 | **T3 Code를 기준 디자인으로 삼는다** | 화면 구조·배치·모양을 정해야 하면 "T3 Code에서는 어떻게 하는가"를 먼저 본다. 우리 앱만의 상태와 컴포넌트만 새로 정한다 | §3 |
| P1 | **대화가 기본이고, 화면은 이유가 있을 때만 둔다** | 대화로 끝낼 수 있으면 대화로 한다. 화면을 두는 이유는 §6 | S3-1, S5-1, S7-3, S10-3 |
| P2 | **신뢰가 걸린 말은 앱이 직접 한다** | 비밀 입력, 쓰기 승인, 안전 경고, 정책은 AI의 말이 아니라 앱의 말로 보이게 하고, 겉모습부터 구별한다 | S2-1, S4-3, S8-1, S10-1 |
| P3 | **학교 데이터에는 출처, 시점, 원문을 붙인다** | 목록이나 수치처럼 확인이 필요한 답에는 출처·조회 시각·원문 링크를, 짧은 답에는 출처를 붙인다 | S3-1, S3-2, S4-1, S5-1 |
| P4 | **할 수 없는 것은 먼저 말한다** | 막힌 뒤 알리기보다 시작 전에 조건을 보인다 | S1-1, S1-6, S9-2 |
| P5 | **막히면 원인과 다음 행동 하나를 준다** | 오류 종류를 보여 주는 대신 지금 할 수 있는 행동을 버튼이나 문장 하나로 준다 | S1-2, S2-3~S2-7 |
| P6 | **끊겨도 하던 일을 잃지 않는다** | 재로그인이나 오래 걸리는 작업이 끼어들어도 원래 요청과 대화가 이어지고, 기다리는 동안 다른 일을 할 수 있다 | S2-1, S2-3, S7-1, S7-2 |
| P7 | **학생의 AI 환경을 존중한다** | 앱 고유 방식보다 터미널에서와 같은 감각을 고른다. 지원하지 않는 것은 이유와 대안을 준다 | S1-3, S9-1, S9-2 |
| P8 | **틀릴 여지를 줄이는 입력을 준다** | 자유 입력보다 앱이 아는 값에서 고르게 한다 | S1-7 |

**우선순위**: P2 > P6 > P1 > 나머지. P0은 모양을 정하는 기준이고, 위 원칙과 부딪치면 위 원칙을 지키는 방향으로 T3 Code의 것을 고쳐 쓴다.

- 예: S4-3에서 대화로 끝내는 편이 빠르지만(P1), `Peer` 원문은 앱의 우측 패널로 보낸다(P2).
- 예: S2-1에서 OTP 입력은 대화를 끊지만 앱 화면에서 받고(P2), 입력이 끝나면 원래 질문이 이어진다(P6).

## 7. 화면 구성

T3 Code 경로는 기준 버전의 `apps/web/src/components/` 기준이다.

### 7.1 내비게이션 골격

```
[좌측 사이드바]                 [본문]     [우측 패널]
  새 대화                         대화       Peer 원문 (필요할 때만 앱이 연다)
  대화 목록 (대화별 상태 라벨)
  ─────────
  연결 알약 (문제가 있을 때만)
  유틸리티 줄: 설정
```

| 영역 | T3 Code 기준 | 우리 것 |
|---|---|---|
| 좌측 사이드바 | `Sidebar.tsx`, `sidebar/*`의 구조(헤더, 새 대화, 목록, 하단) | 프로젝트 묶음·고정·미루기·정리 없이 대화 목록 하나 |
| 하단 알약 | `SidebarProviderUpdatePill`의 자리와 모양 | 내용을 **연결 상태 모음**으로 바꾼다(§7.4). 누르면 설정 > 연결 |
| 하단 유틸리티 줄 | `SidebarUtilityMenu`의 설정 아이콘 버튼 | 설정만 둔다 |
| 계정(아바타와 이름) | 설정 화면 사이드바 하단(`T3ConnectSidebarSignIn` 자리) | 학생 이름(Canvas 내 프로필, 로그인 때 저장). 연결 상태와 관계없이 이름을 보인다. 근거 시나리오는 없고 T3 Code 구조를 따르는 자리다 |
| 우측 패널 | `RightPanelSheet` | `Peer` 원문 보기만 쓴다 |

- 사이드바에는 출처별·제공자별 로그인 상태를 두지 않는다. 연결이 몇 개로 늘어도 알약 하나로 모은다. 학생은 어느 서비스가 끊겼는지 사이드바에서 구분할 필요가 없고, 알약을 누르면 설정에서 행별로 본다.

| AI 설치 동의 | C1, C4 | S1-1 |
| 연결 로그아웃 확인 | C1 | S10-3. T3 Code의 Sign out 확인 창을 따른다. AI 로그아웃은 터미널 로그인도 풀린다는 것을 함께 알린다 |

- 학생지원시스템 로그인은 온보딩에 넣지 않는다. 학생지원시스템이 필요한 질문을 했을 때 창을 띄운다.
- 우리 앱만의 컴포넌트(학교 연결 카드, OTP 창, 쓰기 확인 카드, `Peer` 요약 표시와 원문 보기, 작업 카드, 학과 선택, 정책 화면)도 T3 Code의 기본 부품(dialog, alert, badge, wizard 등)을 조합해 만든다.

### 7.3 MVP 이후 화면

시나리오 근거만 적는다. 구성은 도입할 때 정한다. A3(이번 주 할 일)는 대화로만 다룬다.

| 화면 | 근거 Actor |
|---|---|
| 과목(자료, 공지, 과제) | A4 |
| 공지 | A5 |
| 학적·출결 | A6 |
| 학습 자료(결과물 모음) | A7 |
| 캘린더 | A8 |

### 7.4 대화별 상태

진행 상황은 작업 단위가 아니라 **대화 단위의 상태**로 사이드바에 알린다. T3 Code의 아이콘, 라벨, 색, 우선순위(`Sidebar.logic.ts`의 `resolveSidebarThreadStatus`, `sidebar/SidebarThreadRow.tsx`)를 그대로 쓰고 우리 상태를 대응시킨다. 한 대화에 여러 상태가 겹치면 위에 있는 것 하나만 보인다.

| 우선순위 | T3 Code 상태 | 우리 상태 |
|---|---|---|
| 1 | Approval | 쓰기 확인, 권한 확인 대기 |
| 2 | Input | OTP 입력, 학생지원시스템 로그인 대기 |
| 3 | Working(경과 시간 표시) | AI 응답 중, 이 대화에서 시작한 오래 걸리는 작업 진행 중 |
| 4 | Limited | AI 사용 한도 |
| 5 | Failed | 응답 또는 작업 실패 |
| 6 | Done | 보지 않은 완료 |

- T3 Code의 Request, Woke, Waiting, Preparing은 대응하는 상태가 없어 쓰지 않는다.
- 동영상별 진행률 같은 세부 진행 정보는 MVP에서 보이지 않는다. 대화 안의 작업 카드에는 상태 문구와 취소 버튼만 둔다.
- 앱 창이 뒤에 있을 때의 OS 알림은 MVP에 없다.

**연결 알약**: 연결 행(§7.5) 중 문제 상태(점이 있는 상태)인 것의 개수를 보인다. 문제가 없으면 보이지 않는다.

### 7.5 설정

T3 Code의 설정 모달(왼쪽 내비게이션 그룹, 오른쪽 내용)을 그대로 쓰고 항목만 우리 것으로 채운다.

| 그룹 | 항목 | 내용 |
|---|---|---|
| 일반 | 화면 | 테마: 시스템(기본)·라이트·다크 |
| | 학과 | 학과 1~2개, 목록에서 선택 |
| 연결 | 학교 계정 | Canvas·LearningX·스마트출결(같은 SSO). 한 행이다 |
| | 학생지원시스템 | 별도 로그인 |
| | AI | 제공자마다 한 행. MVP는 Claude Code 하나 |
| 정보 | 정책 | S10-1, S10-2. 내용의 원문은 `cdx policy`와 같다(`GetPolicy`) |
| | 앱 정보 | 버전, 오픈소스 라이선스(§3) |

**연결 행**: T3 Code Providers 목록 행(`settings/ProviderInstanceCard.tsx`: 아이콘, 이름, 2줄 상태, 문제 있을 때만 점, 버튼 순서)을 학교 계정·학생지원시스템·AI가 **모두 같은 모양과 같은 상태 체계로** 쓴다. T3 Code는 서비스마다 상태 판정이 따로 있어 표시가 어긋나는데, 우리는 판정을 한 곳에 둔다.

| 상태 | headline 예 | 점 | 행동 버튼 |
|---|---|---|---|
| 확인 중 | 확인하는 중 | 없음 | 없음 |
| 설치 안 됨(AI만) | 설치가 필요해요 | 빨강 | 설치 |
| 로그인 필요 | 로그인이 필요해요 | 빨강 | 로그인 |
| 곧 만료 | ○월 ○일 만료 예정 | 노랑 | 갱신 |
| 사용할 수 없음 | 플랜 미지원 / 사용 한도 / 학교 시스템 장애 | 빨강 | 원인별 하나(P5) |
| 연결됨 | 학교 계정은 학생 이름, AI는 구독 종류로 연결됨(예: Claude Pro로 연결됨). 이메일은 보이지 않는다 | 없음 | 로그아웃(확인 창) |

- 출처별 장애(LearningX만 안 됨 등)는 로그인 상태가 아니므로 학교 계정 행의 "사용할 수 없음" 원인으로 보인다.
- 로그인 버튼은 T3 Code처럼 진행에 따라 로그인 → 취소 → 다시 시도로 바뀐다.
- **온보딩 카드, 설정 행, 연결 알약, 대화 안 안내가 모두 같은 판정 결과를 쓴다.** 대화 안에서 연결 문제가 나면 앱 메시지에 해당 연결 행으로 바로 가는 버튼을 둔다(T3 Code 모델 선택기의 "Open provider setup"과 같은 방식).

## 8. 상태, 오류, 긴 작업

상태 목록 자체는 [Design Process ②](03_design_process.md)가 기능마다 만든다. 이 절은 어디에, 어떤 원칙으로 보일지만 정한다.

| 무엇 | 위치 |
|---|---|
| 대화 중에 생긴 상태와 오류 | 그 대화 안의 앱 메시지. AI 메시지와 구별한다(P2) |
| 대화 밖에서 계속되는 상태 | 좌측 사이드바의 대화별 상태(§7.4) |
| 계정 연결 문제(만료 예고 등) | 연결 알약, 설정의 해당 연결 행 |
| 오래 걸리는 작업 | 대화 안의 작업 카드(상태 문구, 취소 버튼), 사이드바의 Working |

**오류별 다음 행동**(P5). 문구가 아니라 행동만 정한다.

| 오류 | 다음 행동 |
|---|---|
| `NeedsLogin` | 해당 로그인 창(OTP, 학생지원시스템) 또는 해당 연결 행 |
| `NotAvailable` | 안 되는 출처·기능과 나머지는 쓸 수 있다는 안내 |
| `SourceChanged` | 학교 사이트가 바뀌어 앱 업데이트가 필요하다는 안내 |
| `Temporary` | 다시 시도 |
| `Rejected` | 거절된 이유 |
| `AiUnavailable` | 원인별: 설치 / 로그인 / 한도가 풀리는 시각 / 유료 플랜 안내(사유 열거형은 [application §4.5](layers/02_application.md#45-application-오류)) |
| `ComponentMissing` | 복구 방법별: 설치 프로그램 다시 실행 / OS 설정 열기 |

## 9. AI 응답 경험 원칙

이 원칙을 프롬프트로 옮기는 일은 [entrypoints `ToolGuide`](layers/04_entrypoints.md)가 맡는다([entrypoints §6](layers/04_entrypoints.md#6-toolguide)).

| # | 원칙 |
|---|---|
| R1 | 목록이나 수치로 답할 때는 출처, 조회 시각, 원문 링크를 붙인다. 짧은 답에는 출처만 붙인다(P3). 프롬프트에는 "기준이 명확하지 않으면 모델이 스스로 판단해 정한다"를 함께 넣는다 |
| R2 | 학교 데이터는 추측하지 않고 조회한다. 조회 결과가 없으면 없다고 말한다 |
| R3 | `Peer` 내용은 요약임을 밝히고, 원문은 앱에서 볼 수 있다고 안내한다 |
| R4 | 앱이 하지 않는 일을 요청받으면 거절하고 이유와 정책을 말한다([`cdx policy`](layers/04_entrypoints.md#4-cdx-명령)) |
| R5 | 학생이 쓴 언어로 답한다 |

## 10. 문구 원칙

정확한 문구, 용어, 한글 표기 규칙은 [Design Process](03_design_process.md)의 Foundation이 정한다. 이 절은 그 규칙이 지킬 원칙만 둔다.

| # | 원칙 |
|---|---|
| W0 | 앱의 말은 **해요체**로 쓴다 |
| W1 | 앱의 말은 사실과 행동만 짧게 한다. 꾸밈말과 사과를 반복하지 않는다 |
| W2 | 오류 문구는 원인 한 문장과 다음 행동 하나로 쓴다(P5) |
| W3 | 내부 용어(`OtpRequired`, SSO, 세션 쿠키 등)를 학생에게 보이지 않는다. 학생이 실제로 쓰는 말로 쓴다 |
| W4 | 학생 탓으로 쓰지 않는다. "잘못 입력하셨습니다"가 아니라 "OTP가 맞지 않아요. 다시 입력해 주세요"처럼 쓴다 |
| W5 | 할 수 없는 것을 말할 때는 대안을 함께 쓴다(P4) |

## 12. 아키텍처에 올릴 것

경험상 필요하지만 아키텍처에 아직 없는 것이다. 설계 변경은 해당 문서에서 따로 한다. 반영되면 이 표에서 지우고 해당 문서를 링크한다. 번호는 다시 쓰지 않는다.

반영된 것: ① 플랜 미지원·한도 해제 시각([application §4.5](layers/02_application.md#45-application-오류), [ai_adapters §2](layers/05_ai_adapters.md#2-claude-로그인)), ② 학과 1~2개와 다른 학과 공지([application §3](layers/02_application.md#3-유스케이스-후보), [06_school_site §3](layers/data_access/06_school_site.md#3-학과-공지)), ③ `cdx policy`([entrypoints §4](layers/04_entrypoints.md#4-cdx-명령)), ④ AI 응답 원칙의 `ToolGuide` 반영([entrypoints §6](layers/04_entrypoints.md#6-toolguide)), ⑤ 연결 상태 모음과 대화별 상태의 판정 위치(`presenters/shell`, [presentation §1](layers/03_presentation.md#1-개요)), ⑥ 학생 이름 저장([application §3](layers/02_application.md#3-유스케이스-후보)), ⑦ 테마 저장 위치([presentation §2.2](layers/03_presentation.md#22-디자인-토큰)).

현재 남은 항목은 없다. 새로 생기면 `| # | 필요한 것 | 지금 상태 | 제안 | 관련 문서 |` 표로 적는다. 다음 번호는 ⑧이다.
